# 方案 Agent RSI 单轮试点

RSI 以已保存的方案对比报告为起点，使用报告中的基线失败摘要生成两个提示词候选。在独立验证集上选优后，只让胜出的候选接触留出集。合格结果进入 Console 审批。批准记录保存候选和审批人，供维护者推广，生产默认配置由现有流程管理。

## 运行

1. 按[方案实验说明](planning-experiments.md)运行一次真实对比，并保留报告及快照产物。
2. 在同一隔离数据目录创建 RSI manifest。配置 `sourceReportId`、`validation` 和 `holdout`。其中 `validation` 采用方案实验的 manifest 结构，第一个版本与来源报告的基线完全一致。`holdout` 是不参与候选生成和选择的案例数组。
3. 来源报告、验证集和留出集使用不同案例。每个评估集最多四个案例。留出集覆盖验证集使用的每类场景。
4. 构建后执行 `npm run rsi --prefix temporal -- /absolute/rsi.json round-1`。复用实验的 Temporal、Docker 网络、数据目录和工作目录设置。一个运行键对应同一轮次。
5. 在 Console 的「方案实验」页检查对比证据与候选提示词。维护者使用 GitHub 登录后可审批。由运维通过 `LOOM_RSI_REVIEWER_IDS` 设置允许审批的 GitHub 数字账号 ID，多个 ID 以逗号分隔。审批操作写入 Loom 主数据库，实验数据库继续只读。批准后需要维护者将该候选投入下一轮或生产推广流程。

## 门槛与边界

- 改进 Agent 只收到基线提示词和失败摘要。候选只允许修改提示词，沿用相同的模型、镜像、工具权限和评分规则。
- 验证通过要求至少改善一个案例、保留基线已通过的案例，并且没有结构、证据或范围违规。只评估最高收益候选的留出集。该候选必须通过全部留出案例。
- 每轮最多两个候选，最长 90 分钟。无法生成可靠候选或实验运行失败时，从 Temporal 执行记录检查原因。所有沙箱采用方案实验的只读执行方式。
- 第一轮需要来源报告存在可用的基线失败证据。只有基础设施错误时不会生成候选。
