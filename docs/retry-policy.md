# 失败重试与自动中止

适用于 Loom 的 Python Worker 和 Temporal 试点。本文定义建议策略与验收要求，具体操作以代码中已经启用的策略为准。

## 背景

生产 Issue #15 曾停留在方案评论发布阶段。Worker 每次遇到 `HTTPError` 后约一分钟再试，缺少总次数和总时限。只读排查确认 GitHub App 可以取令牌、读取 Issue 和列出评论。历史记录仅保留异常类型，无法确定发布请求的具体 HTTP 状态。

## 默认策略

| 参数 | 建议默认值 |
| --- | --- |
| 预算键 | 仓库、Issue、方案版本、操作名 |
| 最大尝试次数 | 6 次，含首次执行 |
| 指数退避 | 首次等待 30 秒，之后乘以 2，单次上限 15 分钟 |
| 抖动 | 在基准等待上增加 0–20% 随机时间，结果仍受上限约束 |
| 最长重试窗口 | 从首次尝试开始 30 分钟，包含执行和等待 |
| 单次超时 | 按操作设定，GitHub HTTP 请求建议 15 秒，沙箱任务单独设定 |

服务器提供有效的 `Retry-After` 或明确的限流重置时间时，下次尝试不得早于该时间。若已耗尽次数，或剩余窗口不足以安排新的尝试，进入 `Stopped`。失败计数和下一次尝试时间必须跨进程重启保留。等待期间释放执行槽。

## 错误分类

| 情况 | 处理 |
| --- | --- |
| 临时网络故障、连接超时、HTTP 5xx | 重试。对可能已完成的写请求先查询已有产物。 |
| HTTP 429，或带限流证据的 HTTP 403 | 按服务器指示与退避的较晚时间重试。 |
| HTTP 401 | 允许刷新 GitHub App 令牌一次。刷新后仍失败则中止。刷新后重发计入尝试预算。 |
| 权限不足、目标不可访问、请求校验失败 | 给出脱敏原因并中止。对可能已完成的请求，先按稳定标识查询。 |
| 等待人工审批、基准提交变动、代码验证失败 | 由业务流程处理。等待审批不消耗预算，基准变更触发新版方案，验证失败走单独限次的修复分支。 |

## 持久化与幂等

- 每个阶段操作保留尝试次数、首次尝试时间、下次尝试时间、失败类别、HTTP 状态、GitHub 请求 ID 和中止原因。Console 应展示 `待重试` 与 `已中止`，并可按 Issue 和阶段查看历史。
- 方案评论使用稳定的方案标记。草稿 PR 使用稳定的交付分支和提交关联。响应丢失或进程退出后先查询已有评论、分支或 PR，再决定是否重发。
- Python Worker 在 SQLite 保存状态，与任务领取事务配合，避免同一个操作被并发重试。Temporal 由 Activity 拥有自动重试预算，同一外部请求只设一层重试。限流延迟和永久失败使用对应的 Activity 失败语义，业务状态由 Workflow 更新。
- HTTP 状态和请求 ID 可用于诊断。令牌、私钥、Authorization、Cookie 和原始凭证不得进入日志。

## 人工操作和验收

- **停止重试**阻止新的尝试。正在进行的外部写操作可能已经生效，恢复前需核对结果。
- **立即重试**由授权维护者开启下一轮预算，继续原操作并复用已有方案或补丁。
- **重新规划**在需求、文件范围或基准变化时创建新版本，重新等待审批。
- 自动中止、人工动作和处理结果均写入审计。启用策略时，已超过预算的旧任务应保留历史和产物，并进入中止状态。
- 验收覆盖 Worker 重启、权限错误、限流、排队期间人工停止、预算耗尽、写成功但响应丢失，以及不同 Issue 并行但同一操作不会被重复领取。
